Paso 1: el enunciado y sus requisitos

La biblioteca del recinto presta libros y laptops a los estudiantes. Cada material tiene un código y un título. Un libro tiene un autor y se presta por 14 días; una laptop tiene una memoria RAM y se presta por 3 días. La biblioteca agrega materiales, busca un material por su código, lo presta y lo devuelve. Un material prestado no se puede prestar otra vez. Al cerrar, el sistema guarda el catálogo en un archivo y lo carga al abrir. Si el archivo no existe, el programa avisa sin caerse.

Requisitos no funcionales del proyecto: C++17, compila sin avisos con -Wall -Wextra, datos en un archivo de texto.

Cada requisito es una oración que se puede comprobar. Pulse uno para ver de dónde sale.

Paso 5, v1: las clases y la herencia

class Material {
public:
    virtual ~Material() = default;
    virtual string tipo() const = 0;
    virtual string dato() const = 0;
    virtual int diasPrestamo() const = 0;
    ...
private:
    string codigo;
    string titulo;
    bool prestado = false;
};

= 0 deja la función sin cuerpo: Material es abstracta y nadie puede crear «un material» a secas.

Los datos quedan en private: encapsulación.

class Libro : public Material {
public:
    Libro(const string& c, const string& t, const string& a)
        : Material(c, t), autor(a) {}
    string tipo() const override { return "Libro"; }
    string dato() const override { return autor; }
    int diasPrestamo() const override { return 14; }

private:
    string autor;
};

El constructor de Libro le pasa el código y el título al de Material.

override le pide a g++ que confirme que esa función sí reemplaza una de la base.

class Laptop : public Material {
public:
    Laptop(const string& c, const string& t, int r)
        : Material(c, t), ram(r) {}
    string tipo() const override { return "Laptop"; }
    string dato() const override { return to_string(ram) + " GB"; }
    int diasPrestamo() const override { return 3; }

private:
    int ram;
};

Misma forma, otras respuestas: 3 días y la RAM como dato.

Añadir un tipo nuevo (revistas, calculadoras) es escribir otra clase, sin tocar Material.

int main() {
    Libro  a("LIB-101", "Programacion en C++", "R. Rivera");
    Laptop b("LAP-01", "Equipo sala 1", 8);

    vector<Material*> lista = {&a, &b};
    b.prestar();
    for (Material* m : lista)
        m->mostrar();
    return 0;
}

m->mostrar() es la misma línea para los dos, pero cada objeto contesta tipo() a su manera: polimorfismo.

v3: el catálogo vive en un archivo

void cargar(const string& nombre) {
    ifstream arch(nombre);
    if (!arch)
        throw runtime_error("no se pudo abrir " + nombre);
    string tipo, codigo, titulo, dato, estado;
    while (getline(arch, tipo, ';') && getline(arch, codigo, ';') &&
           getline(arch, titulo, ';') && getline(arch, dato, ';') &&

        unique_ptr<Material> m;
        if (tipo == "Libro")
            m = make_unique<Libro>(codigo, titulo, dato);
        else  // stoi("8 GB") devuelve 8
            m = make_unique<Laptop>(codigo, titulo, stoi(dato));
        ...

Cada línea del archivo es un material, con sus campos separados por ;.

Si el archivo no abre, cargar no imprime nada: lanza una excepción y que main decida.

string registro() const {
    return tipo() + ";" + codigo + ";" + titulo + ";" + dato() + ";" +
           (prestado ? "1" : "0");
}

void guardar(const string& nombre) const {
    ofstream arch(nombre);
    if (!arch)
        throw runtime_error("no se pudo escribir " + nombre);
    for (const auto& m : materiales)
        arch << m->registro() << endl;
}

registro() está en Material: cada objeto sabe escribirse en una línea.

guardar() está en Biblioteca y solo recorre la lista. Ninguna clase hace el trabajo de la otra.

$ g++ -std=c++17 -Wall -Wextra -o biblio main.cpp $ ./biblio Prestado: LIB-102 Prestado: LAP-01 Disponibles: 1 de 4

main carga el catálogo, presta LIB-102 y LAP-01, y lo guarda al terminar.

LAP-02 ya venía prestada en el archivo: por eso queda 1 de 4.

$ cat catalogo.txt Libro;LIB-101;Programacion en C++;R. Rivera;0 Libro;LIB-102;Redes para todos;A. Colon;1 Laptop;LAP-01;Equipo sala 1;8 GB;1 Laptop;LAP-02;Equipo sala 2;16 GB;1

El último campo es prestado: 1 o 0.

Antes de la corrida 1, LIB-102 y LAP-01 tenían 0. El programa terminó, pero el préstamo quedó escrito.

$ ./biblio Error: LIB-102 ya esta prestado Error: LAP-01 ya esta prestado Disponibles: 1 de 4

Misma orden, otro resultado: el programa se acuerda de la corrida anterior porque la leyó del archivo.

La excepción de prestar() se atrapa y el programa sigue.

$ rm catalogo.txt $ ./biblio Error: no se pudo abrir catalogo.txt $ echo $? 1

Sin archivo, main atrapa la excepción, avisa y termina con return 1. No se cae.

$ cat catalogo.txt Libro;LIB-101;Programacion en C++;R. Rivera;0 Laptop;LAP-03;Equipo sala 3;ocho GB;0 $ ./biblio Error: stoi

stoi("ocho GB") lanza invalid_argument, que también es una exception.

El mensaje «stoi» dice poco. Un buen proyecto diría en qué línea del archivo está el problema.

    Las preguntas que siempre llegan
    
  
    
    
    ¿Por qué herencia y no un solo tipo con un campo «tipo»?Porque cada tipo responde distinto (días, dato). Con un campo habría un if en cada función; con herencia, un tipo nuevo es una clase nueva.
    
    
    ¿Qué pasa si el archivo no existe o está dañado?Muéstrelo: la corrida sin archivo y la excepción atrapada. Si hay un caso que no manejan, díganlo como mejora pendiente.
    
    
    ¿Cómo saben que funciona?Con el plan de pruebas: qué se prueba, qué se espera y la corrida con todas en OK. «Lo probé y sirvió» no es una respuesta.
    
    
    ¿Qué parte hizo cada uno?El tablero y el historial de Git lo dicen. Cada miembro debe poder explicar cualquier clase, no solo la suya.
    
    
    ¿Qué cambiarían si empezaran de nuevo?Una lección concreta: «separaríamos antes en .h y .cpp» vale más que «nos organizaríamos mejor».
    
    
    ¿Cómo añadirían un tipo nuevo, por ejemplo revistas?Una clase Revista : public Material con sus tres funciones, y una línea más en cargar(). Las demás clases no cambian.
